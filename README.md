# Vantage-Authority Resolution Profiles for ERC-8309

**Authors:** Damon Zwicker, Tiago Merlini, Jimmy Shi, Pavlo Tvardovskyi, babyblueviper1

**Companion specification — current cut: [v0.3.9](./8309-vantage-authority-companion-v0.3.9.md)**

This document defines what a system does once ERC-8309's mesh has surfaced a divergence — two or more vantages reporting different values for the same observation — and no base rule says which value wins. ERC-8309 preserves divergence rather than silently deduplicating it; this companion defines the resolution layer on top: a three-state fault taxonomy, a resolution envelope (E1–E6) and verdict (V1–V5) that make every resolution's inputs recomputable, an output taxonomy with no false green and no false red, and four resolution profiles (A: divergence surfacing, the normative default that resolves nothing; B: quorum; C: registry-weighted; D: declared priority). Profile A runs in production as the ingestion boundary for TSEI. Every serializer, schema, and conformance claim in the document is bound explicitly, never inferred, and the reference implementation it cites is pinned by digest over structured evidence that anyone can recompute. It is co-authored by the five members of the working group that built and reviewed it, each having chosen co-authorship individually; the base standard it extends is ERC-8309 (ethereum/ERCs#1826).

Read §13 before anything else if you want to know whether to trust the rest. It is the document's provenance record: every design decision, every ratification vote, every correction, and every landing of code to canonical main is a row citing the message, commit, or ratification that produced it — and it is append-only. Rows are never edited once a cut has circulated; a correction is a new row that supersedes the old one by reference, so the record of what was wrong survives alongside the fix. Several rows record errors the document made about itself — a cut date that didn't match its bytes, a misattributed finding, a deployment note placed under the wrong profile, a claim that outran what a recompute had actually verified — each caught by a co-author checking the artifact rather than the summary. That the record shows the document's own mistakes is the point: a specification whose §13 only recorded successes would be one you'd have to take on faith.

Cuts are how the document moves. Each version is a distinct set of bytes with a cut date that is a claim about exactly those bytes; if the bytes change, the date changes and so does the version. A cut circulates to the working group for an artifact-level read — checked against the file, not the announcement — and is either ratified or corrected in the next cut. Every circulated cut is preserved here as its own file in `cuts/`, never overwritten and never edited after circulation, so any claim in the current cut about what an earlier one said can be checked by diffing the files rather than trusting the sentence. Correction cuts are small, frequent, and deliberately numbered rather than re-issued in place. New rows land in §13 as events happen — a merge to canonical main, an independent recompute, a ratification — and the "Next" list at the end of the current cut states what remains open and who owns it. If you find an error, the right shape for reporting it is the one this repo's co-authors use: name the section, quote the bytes, say what the record actually shows.
